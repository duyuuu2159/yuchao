# 性能：怎么测的，慢在哪里，改了什么

## 怎么测

```bash
node scripts/bench.ts                              # 1000 个会话 × 100 条消息
node scripts/bench.ts --sessions 3000 --messages 120
node scripts/bench.ts --json                       # 机器可读，方便对比
```

`scripts/bench.ts` 按固定种子生成 Claude Code 格式的会话：中文提问、带代码块的回答、工具调用和工具输出按 1:1:1:1 交替。不读取本机任何真实会话，所以任何人都能复现同样的数据。它测四件事：

- **冷索引**：空数据库，全部解析写入
- **无变化**：再索引一次，所有文件都应该跳过
- **改动 1%**：给 1% 的会话追加一条消息，只重新解析这些文件
- **搜索**：8 个查询，每个跑 20 次，取 P50 / P95（含一个两字词「权限」，它走的是 LIKE 而不是全文索引）

合成数据和真实数据形状不同（见下文），所以除了基准，每项改动也在作者本机的真实索引（约 6.5 万条消息、534 MB）的副本上对比过。

测试机：Xeon E5-2686 v4，Windows，Node 24.18。

## 结果

| | 优化前 | 优化后 | |
|---|---|---|---|
| 冷索引（10 万条） | 13.1 秒 | 4.8–5.7 秒 | 约 2.5 倍 |
| 搜索 P50（10 万条合成） | 69 毫秒 | 9.7 毫秒 | 约 7 倍 |
| 搜索 P95（10 万条合成） | 113 毫秒 | 33 毫秒 | 约 3.4 倍 |
| 搜索 P50（真实数据） | 70.8 毫秒 | 14.7 毫秒 | 约 4.8 倍 |
| **搜索 P95（真实数据）** | **264 毫秒** | **17 毫秒** | **约 15 倍** |
| 增量更新（改动 1%） | 225 毫秒 | 370 毫秒 | 慢了，见第 5 条 |

36 万条消息（3000 个会话）时：冷索引 16.6 秒（约 2.2 万条/秒，基本线性），搜索 P50 32 毫秒、P95 110 毫秒。

## 过程

### 1. 先找到问题：搜索时间涨得比数据量快

第一次跑基准，1 万条消息时搜索 P50 是 2 毫秒，10 万条时 69 毫秒——数据多 10 倍，搜索慢 35 倍。而且命中多的常见词（nginx、systemctl）最慢，同时要求两个词的查询反而很快。

### 2. 看查询计划，再拆开计时

`EXPLAIN QUERY PLAN` 显示：全文索引给出命中的 id → 逐个回 messages 表取时间和角色 → 用临时 B 树全部排序 → 取前 80 条。

拆开计时（nginx，命中 6051 条）：

| 步骤 | 耗时 |
|---|---|
| 只从全文索引取命中 id | 5.5 毫秒 |
| 加上回表读时间和角色 | 43.6 毫秒 |

全文索引本身很快，**慢的是回表**：6000 次按 id 查找，平均每次 6 微秒。

### 3. 页缓存太小（改了）

SQLite 默认页缓存 2 MB，数据库 30 MB，回表时几乎每次都要重新读页。`PRAGMA cache_size = -65536`（64 MB 上限，按需占用）后，nginx 从 60 毫秒降到 15 毫秒，两字词从 88 降到 33。同时试了 `mmap_size`，效果相同，两个都开没有额外收益，所以只留一个。

### 4. 排序时不带正文（改了）

原来的查询一步到位：`SELECT ... m.text ... ORDER BY ... LIMIT 80`，几千行连同正文一起进排序器。改成两步：先只用 id 和时间排出前 80 条，再按 id 取回正文。叠加大缓存后，nginx 从 15 毫秒降到 9 毫秒。

### 5. 两字词扫了不该扫的消息（改了，有代价）

trigram 全文索引只能匹配 3 个字以上的词，「报错」「回滚」这类两字词只能 `LIKE` 逐条扫。真实数据里工具调用和工具输出占消息的八成以上，而搜索默认只看用户和 agent 的话。加了 `messages(role, ts)` 索引后，`LIKE` 只扫对话：真实数据上两字词从 79 毫秒降到 16 毫秒。

**副作用一**：SQLite 对全文检索的查询也开始用这个索引——先扫全部对话，再逐条比对是否在全文命中里，常见词慢了一倍。解决办法是在有全文检索词时写成 `+m.role IN (...)`：一元 `+` 让这个条件不参与选索引，查询仍然从全文索引的命中 id 出发。

**副作用二**：每条消息多维护一个索引项，合成数据上的增量更新从 225 毫秒变成约 370 毫秒，冷索引也慢了约 0.5–1 秒。合成数据里对话占一半，索引帮不上太多；真实数据里对话只占一成多，搜索快了 5 倍。增量更新在后台进行，用户感觉不到这 0.15 秒，而搜索是用户在等，所以保留。

### 6. 冷索引：九成时间花在全文索引上（改了）

拆开计时，10 万条消息：

| | 耗时 |
|---|---|
| 只解析 JSONL | 1.3 秒 |
| 只写普通表 | 0.8 秒 |
| 写普通表 + 触发器逐行更新 trigram 全文索引 | 9.9 秒 |
| 写普通表，最后一次性 `rebuild` 全文索引 | 0.8 + 1.5 秒 |

所以首次建索引（以及解析规则升级后清空重建）时改成批量模式：去掉两个触发器，只写 messages 表，最后 `rebuild`。日常增量只改几个文件，`rebuild` 要把全表重算，对增量反而更慢，所以增量继续用触发器。

批量模式要处理好三件事：

- **原子性**：去掉触发器、写入、重建、恢复触发器都在一个事务里。中途出错或进程被杀，数据库回到开始前的样子，不会留下「触发器没了、索引建了一半」的状态。测试里用 `onProgress` 回调在第二个文件时抛错来验证。
- **单个文件出错不影响其它文件**：每个文件包在 `SAVEPOINT` 里。
- **之后的增量写入不能变慢**：只做 `rebuild` 的话，后续每次增量写入都要和 rebuild 留下的段结构做昂贵的自动合并，增量更新从 0.2 秒变成 1.2 秒。在 `rebuild` 之后再做一次 `optimize`，把索引整理成一个段，增量写入就恢复了（甚至比逐行建出来的索引还快）。最后再做一次 WAL 检查点，否则下一次写入要替这个大事务把几十 MB 的 WAL 搬回主库。

测试用 FTS5 自带的 `integrity-check`（`rank = 1` 时会和外部内容表逐条比对）确认批量模式和之后的增量更新都没有让全文索引和数据表不一致。

## 试过但没有用的

| 尝试 | 结果 | 原因 |
|---|---|---|
| 缓存预编译语句，不再每次 `prepare` | 13.4 秒 vs 13.1 秒，没变化 | 瓶颈在全文索引，不在 SQL 编译 |
| 多个文件合并成一个事务提交 | 13.1 秒 → 23.1 秒，**更慢** | 触发器还在时，一个大事务里 FTS5 的待写数据越积越多 |
| `mmap_size` 和大缓存同时开 | 和只开一个相同 | 两者解决的是同一个问题 |

这几项都撤回了：没有收益的改动只会增加复杂度。

## 一处改正

最初的注释写的是「批量模式必须去掉删除触发器，否则外部内容的 FTS5 收到一条从未写进索引的 delete 会把索引弄坏」。写测试时做了反向验证：只去掉插入触发器、保留删除触发器，「同一会话出现在两个文件里」的测试照样通过。原因是最后的 `rebuild` 会丢掉索引里的全部旧数据重新计算，过程中写下的错误删除记录也一起被清掉了。所以去掉删除触发器的真正理由是**省掉白做的工作**，注释已经改正。

## 还没做的

- **常见词在超大数据量下仍然线性增长**：36 万条消息、数据库 114 MB 时，常见词要回表几万次，缓存装不下，P95 到 110 毫秒。下一步可以把 `ts` 存进全文索引的辅助列，排序时不必回表；或者按时间倒序分段检索，凑够条数就停。
- **两字词**：仍然是线性扫描，只是扫的范围小了。可以再加一个 bigram 分词的全文索引，代价是索引体积大约翻倍。
