## 2026-11-09 · M1 统一会话库

### 结果

- 在本机真实数据上：**163 个会话文件**（Claude 76 个，Codex 87 个，原始数据约 1.3 GB），**全部解析成功**
- 首次索引约 65–80 秒，生成 104 MB 的数据库；之后的增量索引约 **2–3 秒**（只重建有变化的文件）
- 18 个自动化测试，覆盖两种格式的解析、增量索引、删除、分叉去重、中文搜索、特殊字符

### 关键决定

**1. 先统一数据模型，再写解析器。**
两种 agent 的格式差别很大：Claude 一行一个事件，工具结果藏在 `user` 消息里；Codex 把消息、工具调用、推理、token 统计都放在 `response_item` / `event_msg` 里。我先定义了一个统一的 `Session → Message` 模型（`src/core/types.ts`），消息只有五种角色：用户、agent、工具调用、工具结果、注入的上下文。后面的索引、搜索、界面都只认这个模型，以后加新的 agent 只需要多写一个解析器。

**2. 区分「我写的话」和「客户端塞进去的话」。**
会话里有大量不是用户亲手写的内容：Codex 每次都注入 `<environment_context>`，Claude 有斜杠命令输出、`[Request interrupted by user]`、对话压缩摘要。如果不区分，搜索结果全是噪音，以后做「用户画像」也会被污染。办法是按开头的固定标记识别（`src/core/text.ts`），归为 `context` 角色，默认不参与搜索。我是先把真实数据里出现最多的用户消息开头统计出来，再决定规则的。

**3. 用 SQLite FTS5 的 trigram 分词做中文搜索。**
中文没有空格，普通的全文索引切不出词。trigram 把文本切成连续三个字的片段，不需要分词词典也能搜中文。代价是少于三个字的词（比如「回滚」）用不了索引，所以短词退回 `LIKE` 逐条扫描。

**4. 增量索引按「修改时间 + 文件大小」判断，有变化就整份重新解析。**
会话文件是追加写入的，理论上可以记住上次读到哪一行、只读新增部分，但那样要处理文件被截断、被改写等情况。单个文件整份重新解析只要几十毫秒，所以选了简单可靠的做法。

**5. 解析器版本号。**
改了解析规则以后，没变的文件会被增量索引跳过，旧的分类结果就一直留着。所以在数据库里存一个版本号（`PRAGMA user_version`），版本不一致就清空重建。这个问题是我改完规则、发现旧数据没更新时才意识到的。

### 踩过的坑

- **超大文件把程序撑爆。** 本机有一个 Codex 会话，zstd 解压后超过了 JavaScript 单个字符串的长度上限，一次性读入直接报 `ERR_STRING_TOO_LONG`。改成边解压边逐行读取（`src/core/lines.ts`）。
- **Codex 会话不全是压缩的。** 正在进行的会话是普通 `.jsonl`，结束后才压缩成 `.zst`，所以两种都要支持。
- **分叉会话导致搜索结果重复。** Claude 从一个会话「分叉」出新会话时，会把整段历史复制过去。真实数据里有 213 组这样的重复。搜索时按「时间 + 角色 + 内容」去重，只保留最早的会话，并标注「另有 N 个分叉会话包含」。
- **Codex 子 agent 的文件里有多条 `session_meta`。** 第二条是父会话的信息，如果用最后一条，子会话的 id 就会被父会话覆盖。只认第一条。
- **测试数据不能用真实会话。** 真实会话里有服务器密码。测试用的样例全部手写（`test/fixtures/`），每个样例对应一个在真实数据里见过的情况。
- **中途打断安装导致原生模块损坏。** 安装依赖时被打断，一个原生模块只写了一半，运行时报 Windows 错误 193。删掉 `node_modules` 重装解决。

### 已知的不足（留给后面）

- 首次索引一分多钟偏慢。大部分时间花在解析 Claude 的 `api-request-blob` 这类巨大但无用的行上，可以先看行首类型再决定要不要 `JSON.parse`。
- Claude 的 `thinking` 和 Codex 的推理内容没有收录（多数为空或已加密）。
- 分叉会话的判断依赖「时间和内容完全相同」，两个分叉会话开始时间相同时，选哪个作为原始会话是按 id 排序决定的，不一定准确。
- 搜索结果按时间倒序，没有按相关度排序。

## 2026-11-09 · M2 安全扫描

### 结果

- 扫描本机全部 **34,184 条消息和 162 个会话标题，用时约 1 秒**
- 发现 **24 个不同的秘密，其中 23 个高风险**，去重后共 299 处出现：
  - 一台服务器的 root 密码出现了 **207 次，散布在 27 个会话里**。源头是一句写着服务器 IP、用户名和密码的话，被 Codex 当成了会话标题，之后每个读取会话列表的 agent 都会再看到并复制一次
  - 19 个 API key，其中 12 个是 agent 为了测试可用性，一次性写进脚本里的
  - 2 段 SSH 私钥，出现在 agent 排查问题时打印出的命令输出里
  - 网站后台管理员的密码
- 第一版规则在真实数据上有 48 条结果，其中一半是误报；逐条分析后改进规则，降到 24 条，剩下的 1 条中风险是测试代码里的假密码
- 报告和界面里 **不出现任何原文**：用脚本检查了完整报告里的 142 段上下文，长串 base64 和 `sk-` 原文都是 0 处
- 测试从 18 个增加到 39 个

### 关键决定

**1. 规则 + 信息熵，而不是只用规则。**
只靠「password 后面跟着的东西」会抓到大量 `password: string`、`your_password`、`process.env.PASSWORD`。所以每个候选值再过一遍判断（`looksLikeSecret`）：排除占位符、变量引用、代码片段，再看它是不是「字母加数字」或者信息熵够高。信息熵衡量一串字符有多随机，随机生成的密码通常每个字符超过 3 比特，英文单词通常低于 3 比特。

**2. 密码旁边有服务器地址，就升级为「服务器登录凭据」。**
单独一个密码是中风险；旁边 120 个字符内有 IP 地址、`root@`、「用户名」，说明这是一整套能直接登录的信息，按高风险处理。

**3. 用指纹把同一个秘密归为一组。**
指纹是秘密原文的 SHA-256 前 16 位。同一个密码出现 200 多次只显示为一条，并标明出现次数和涉及的会话数。指纹无法反推出原文，所以「标记为误报」只需要存指纹，数据库里不保存任何原文。

**4. 默认打码显示。**
以后要给别人演示、截图、录屏，而会话标题里就写着服务器密码。所以接口默认把标题、对话、搜索摘要里的秘密打码，界面上有「显示原文」开关。搜索摘要要先打码再截取，否则秘密被截成两半时识别不出来。

**5. 本地服务也要防攻击。**
扫描接口返回的是「哪里泄露了密码」，本身就是敏感信息。任何网页都能向 `127.0.0.1` 发请求，还能用 DNS 重绑定读取返回值。所以加了两层防护：只接受 Host 为本机的请求；写操作必须带自定义请求头 `x-yuchao`，浏览器跨域发送自定义请求头前必须先预检，而服务不响应预检。

### 踩过的坑

- **打码后的上下文里漏出了另一个秘密。** 一段话里有两个秘密时，给第一个生成上下文，第二个会以原文出现。改成先找出所有秘密，全部打码后再截取；截取边界也不能落在某个秘密中间。
- **私钥只打码了第一行。** 第一版规则只把私钥正文的第一行当作秘密，在真实数据上跑的时候，上下文里露出了后面几行。改成整段正文（包括被转义成 `\n` 的多行）都算作秘密，并加了测试：上下文里不能出现私钥正文的任何一段。这是这次最严重的问题，靠在真实数据上检查输出才发现。
- **真实数据里的误报和测试样例完全不同。** `$PWD`（PowerShell 的当前目录）、`/etc/passwd`、正则表达式里的 `token|secret|password`、英文句子 "pass the password non-interactively."。每一种都加进了测试的「不应报告」列表。
- **分叉会话让数字虚高。** 和 M1 的搜索一样，分叉会话复制的历史被重复计数。按「时间、位置、上下文」去重后，服务器密码从 210 次、29 个会话变为 207 次、27 个会话。
- **Windows 换行符。** 改写提交作者时，git 把工作区文件转成了 CRLF，导致后续按字符串编辑文件失败。加了 `.gitattributes` 统一使用 LF。
- **测试里的假密钥会被 GitHub 拦截。** GitHub 会阻止推送「长得像真密钥」的字符串，所以测试里的假 key 在运行时拼接出来。

### 已知的不足

- 全小写、没有数字的密码（例如 `qwertyzxcv`）会被当成普通单词漏掉，这是为了减少误报做的取舍。
- 只扫描了会话内容，没有扫描各 agent 的配置文件（那里的 key 是正常存放的，扫出来只会是噪音）。
- 扫描是只读的：它告诉你哪里有问题，但不会替你修改会话文件或作废 key。作废泄露的 key 必须到对应平台操作。
