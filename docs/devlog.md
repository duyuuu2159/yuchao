## 2026-11-09 · M1 统一会话库

### 结果

- 在本机真实数据上：**163 个会话文件**（Claude 76 个，Codex 87 个，原始数据约 1.3 GB），**全部解析成功**
- 首次索引约 65–80 秒，生成 104 MB 的数据库；之后的增量索引约 **2–3 秒**（只重建有变化的文件）
- 18 个自动化测试，覆盖两种格式的解析、增量索引、删除、分叉去重、中文搜索、特殊字符

### 关键决定

**1. 先统一数据模型，再写解析器。**
两种 agent 的格式差别很大：Claude 一行一个事件，工具结果藏在 `user` 消息里；Codex 把消息、工具调用、推理、token 统计都放在 `response_item` / `event_msg` 里。我先定义了一个统一的 `Session → Message` 模型（`src/core/types.ts`），消息只有五种角色：用户、agent、工具调用、工具结果、注入的上下文。后面的索引、搜索、界面都只认这个模型，以后加新的 agent 只需要多写一个解析器。

**2. 区分「我写的话」和「客户端塞进去的话」。**
会话里有大量不是用户亲手写的内容：Codex 每次都注入 `<environment_context>`，Claude 有斜杠命令输出、`[Request interrupted by user]`、对话压缩摘要。如果不区分，搜索结果全是噪音，以后做「用户画像」也会被污染。办法是按开头的固定标记识别（`src/core/text.ts`），归为 `context` 角色，默认不参与搜索。我是先把真实数据里出现最多的用户消息开头统计出来，再决定规则的。

**3. 用 SQLite FTS5 的 trigram 分词做中文搜索。**
中文没有空格，普通的全文索引切不出词。trigram 把文本切成连续三个字的片段，不需要分词词典也能搜中文。代价是少于三个字的词（比如「回滚」）用不了索引，所以短词退回 `LIKE` 逐条扫描。

**4. 增量索引按「修改时间 + 文件大小」判断，有变化就整份重新解析。**
会话文件是追加写入的，理论上可以记住上次读到哪一行、只读新增部分，但那样要处理文件被截断、被改写等情况。单个文件整份重新解析只要几十毫秒，所以选了简单可靠的做法。

**5. 解析器版本号。**
改了解析规则以后，没变的文件会被增量索引跳过，旧的分类结果就一直留着。所以在数据库里存一个版本号（`PRAGMA user_version`），版本不一致就清空重建。这个问题是我改完规则、发现旧数据没更新时才意识到的。

### 踩过的坑

- **超大文件把程序撑爆。** 本机有一个 Codex 会话，zstd 解压后超过了 JavaScript 单个字符串的长度上限，一次性读入直接报 `ERR_STRING_TOO_LONG`。改成边解压边逐行读取（`src/core/lines.ts`）。
- **Codex 会话不全是压缩的。** 正在进行的会话是普通 `.jsonl`，结束后才压缩成 `.zst`，所以两种都要支持。
- **分叉会话导致搜索结果重复。** Claude 从一个会话「分叉」出新会话时，会把整段历史复制过去。真实数据里有 213 组这样的重复。搜索时按「时间 + 角色 + 内容」去重，只保留最早的会话，并标注「另有 N 个分叉会话包含」。
- **Codex 子 agent 的文件里有多条 `session_meta`。** 第二条是父会话的信息，如果用最后一条，子会话的 id 就会被父会话覆盖。只认第一条。
- **测试数据不能用真实会话。** 真实会话里有服务器密码。测试用的样例全部手写（`test/fixtures/`），每个样例对应一个在真实数据里见过的情况。
- **中途打断安装导致原生模块损坏。** 安装依赖时被打断，一个原生模块只写了一半，运行时报 Windows 错误 193。删掉 `node_modules` 重装解决。

### 已知的不足（留给后面）

- 首次索引一分多钟偏慢。大部分时间花在解析 Claude 的 `api-request-blob` 这类巨大但无用的行上，可以先看行首类型再决定要不要 `JSON.parse`。
- Claude 的 `thinking` 和 Codex 的推理内容没有收录（多数为空或已加密）。
- 分叉会话的判断依赖「时间和内容完全相同」，两个分叉会话开始时间相同时，选哪个作为原始会话是按 id 排序决定的，不一定准确。
- 搜索结果按时间倒序，没有按相关度排序。

## 2026-11-09 · M2 安全扫描

### 结果

- 扫描本机全部 **34,184 条消息和 162 个会话标题，用时约 1 秒**
- 发现 **24 个不同的秘密，其中 23 个高风险**，去重后共 299 处出现：
  - 一台服务器的 root 密码出现了 **207 次，散布在 27 个会话里**。源头是一句写着服务器 IP、用户名和密码的话，被 Codex 当成了会话标题，之后每个读取会话列表的 agent 都会再看到并复制一次
  - 19 个 API key，其中 12 个是 agent 为了测试可用性，一次性写进脚本里的
  - 2 段 SSH 私钥，出现在 agent 排查问题时打印出的命令输出里
  - 网站后台管理员的密码
- 第一版规则在真实数据上有 48 条结果，其中一半是误报；逐条分析后改进规则，降到 24 条，剩下的 1 条中风险是测试代码里的假密码
- 报告和界面里 **不出现任何原文**：用脚本检查了完整报告里的 142 段上下文，长串 base64 和 `sk-` 原文都是 0 处
- 测试从 18 个增加到 39 个

### 关键决定

**1. 规则 + 信息熵，而不是只用规则。**
只靠「password 后面跟着的东西」会抓到大量 `password: string`、`your_password`、`process.env.PASSWORD`。所以每个候选值再过一遍判断（`looksLikeSecret`）：排除占位符、变量引用、代码片段，再看它是不是「字母加数字」或者信息熵够高。信息熵衡量一串字符有多随机，随机生成的密码通常每个字符超过 3 比特，英文单词通常低于 3 比特。

**2. 密码旁边有服务器地址，就升级为「服务器登录凭据」。**
单独一个密码是中风险；旁边 120 个字符内有 IP 地址、`root@`、「用户名」，说明这是一整套能直接登录的信息，按高风险处理。

**3. 用指纹把同一个秘密归为一组。**
指纹是秘密原文的 SHA-256 前 16 位。同一个密码出现 200 多次只显示为一条，并标明出现次数和涉及的会话数。指纹无法反推出原文，所以「标记为误报」只需要存指纹，数据库里不保存任何原文。

**4. 默认打码显示。**
以后要给别人演示、截图、录屏，而会话标题里就写着服务器密码。所以接口默认把标题、对话、搜索摘要里的秘密打码，界面上有「显示原文」开关。搜索摘要要先打码再截取，否则秘密被截成两半时识别不出来。

**5. 本地服务也要防攻击。**
扫描接口返回的是「哪里泄露了密码」，本身就是敏感信息。任何网页都能向 `127.0.0.1` 发请求，还能用 DNS 重绑定读取返回值。所以加了两层防护：只接受 Host 为本机的请求；写操作必须带自定义请求头 `x-yuchao`，浏览器跨域发送自定义请求头前必须先预检，而服务不响应预检。

### 踩过的坑

- **打码后的上下文里漏出了另一个秘密。** 一段话里有两个秘密时，给第一个生成上下文，第二个会以原文出现。改成先找出所有秘密，全部打码后再截取；截取边界也不能落在某个秘密中间。
- **私钥只打码了第一行。** 第一版规则只把私钥正文的第一行当作秘密，在真实数据上跑的时候，上下文里露出了后面几行。改成整段正文（包括被转义成 `\n` 的多行）都算作秘密，并加了测试：上下文里不能出现私钥正文的任何一段。这是这次最严重的问题，靠在真实数据上检查输出才发现。
- **真实数据里的误报和测试样例完全不同。** `$PWD`（PowerShell 的当前目录）、`/etc/passwd`、正则表达式里的 `token|secret|password`、英文句子 "pass the password non-interactively."。每一种都加进了测试的「不应报告」列表。
- **分叉会话让数字虚高。** 和 M1 的搜索一样，分叉会话复制的历史被重复计数。按「时间、位置、上下文」去重后，服务器密码从 210 次、29 个会话变为 207 次、27 个会话。
- **Windows 换行符。** 改写提交作者时，git 把工作区文件转成了 CRLF，导致后续按字符串编辑文件失败。加了 `.gitattributes` 统一使用 LF。
- **测试里的假密钥会被 GitHub 拦截。** GitHub 会阻止推送「长得像真密钥」的字符串，所以测试里的假 key 在运行时拼接出来。

### 已知的不足

- 全小写、没有数字的密码（例如 `qwertyzxcv`）会被当成普通单词漏掉，这是为了减少误报做的取舍。
- 只扫描了会话内容，没有扫描各 agent 的配置文件（那里的 key 是正常存放的，扫出来只会是噪音）。
- 扫描是只读的：它告诉你哪里有问题，但不会替你修改会话文件或作废 key。作废泄露的 key 必须到对应平台操作。

## 2026-11-09 · M3 Agent 眼中的你

### 结果

- **本地统计**（不调用大模型）：活跃 18 天，亲手写了 561 条消息（分叉会话复制的不重复计算），消息长度中位数 20 字；最活跃的时段是下午 2 点；说得最多的话是「继续」，72 次
- **Claude 已有的记忆**：4 个项目里共 14 条，直接读取展示
- **大模型生成的画像**：75 个会话、约 5.9 万字（密码、密钥、IP 已打码）发给 gpt-6.1-sol，128 秒完成，0 个失败；输入 42.2 万 token，输出 1.26 万 token
- **引用校验**：剔除 0 个不存在的引用、0 条没有依据的结论。这次模型给出的所有引用都能在原始数据里找到；校验逻辑本身由测试覆盖（测试里的假模型会故意给出不存在的编号）
- 画像里的结论比较克制，例如「这些会话不足以判断其独立编程熟练度」；并指出了一个对用户有用的模式：多次把服务器登录信息和 API key 直接发给助手
- 测试从 39 个增加到 58 个

### 关键决定

**1. 「agent 眼中的你」有两个来源，不只靠大模型生成。**
Claude Code 在合作过程中会自己写记忆文件（`~/.claude/projects/*/memory/*.md`），比如「用户要求所有回复用简体中文」「用户不想被反复确认」。这本身就是字面意义上的「agent 眼中的你」，直接读取展示即可，不需要再花钱让模型生成。大模型生成的画像是另一个来源，两者放在同一页对照着看。Codex 的记忆库是空的；`~/.codex/AGENTS.md` 里装的是一段越狱提示词，不是关于用户的记忆，所以不读取。

**2. 本地统计和模型生成分开。**
活跃天数、各时段消息数、最常说的话、项目分布这些是确定的数字，直接从数据库算，不经过模型，也就不会出错、不花钱。只有「这个人擅长什么、做事方式如何」这类需要归纳的内容才交给模型。

**3. 只发用户亲手写的话，并且先脱敏。**
agent 的回复、工具输出、系统注入的上下文都不发送。密码和密钥用 M2 的规则打码，IP 地址替换成 `[IP]`。分叉会话复制的消息只算一次，子 agent 会话里的「用户消息」其实是父 agent 写的，也不算。会话太长时保留开头和结尾，中间明确标出「省略了 N 条」，不悄悄截断。`profile preview` 会把将要发送的完整内容写到文件里，发送前可以逐字检查。

**4. 两步生成，每一步都要求引用出处。**
第一步逐个会话总结，每条观察必须引用消息序号 `[#12]`；第二步把所有总结汇总成画像，每条结论必须引用会话编号 `S3`。汇总时用短编号代替长长的会话 id，既省 token，也降低模型抄错 id 的概率。

**5. 用程序校验引用，而不是相信模型。**
模型给出的序号或编号，程序会核对它是否真的出现在发送的数据里。不存在的引用剔除；一条结论剔除后一个有效引用都不剩，就整条丢掉。剔除了多少条会记录在版本信息里、显示在界面上。这是防止模型编造内容的关键：画像里留下的每句话，都能点开看到原始会话。

**6. 按内容哈希缓存，按版本保存。**
每个会话的总结按「证据文本的哈希 + 模型 + 提示词版本」缓存。会话没变就直接复用，以后增量更新只处理新会话，费用低很多。每次生成的画像都保存为一个版本，可以对比两次之间新增和消失的结论。

**7. 生成必须在命令行里明确执行。**
生成会把数据发给第三方并产生费用，所以网页上只能查看，不提供生成按钮。`profile build` 不加 `--yes` 时，只说明「会把多少内容发到哪个地址、用什么模型」，然后退出。

**8. 用户的 API key 不经过 AI 助手。**
开发过程中用户在聊天里发过两个中转站的 key。开发时没有把它们写进命令或代码，而是提供了几种让程序自己读取的方式：复用 Claude Code 的配置（`--claude-code-config`）、在终端里隐藏输入（`--ask-key`）、从用户自己保存的文件读取（`--key-file`，文件放在代码仓库外面）。最后用的是 key 文件，因为用户在终端面板里没法输入。

**9. 不绑定单一服务商。**
画像流程只依赖一个很小的 `LlmClient` 接口（输入提示词和输出格式，返回校验过的结果）。Claude 用官方 SDK 实现；后来发现用户手上的 key 只能用 GPT 模型，就加了一个 OpenAI 兼容格式的实现，引用校验、缓存、版本都不用改。OpenAI 那边用 JSON Schema 约束输出，返回后再用 zod 校验一遍，不信任接口一定遵守。

### 踩过的坑

- **余额不足时白等好几分钟。** 第一次用 Claude Code 的中转站生成，对方返回「Credits 不足」，程序却把 75 个会话挨个试了一遍，每个还自动重试。改成前 3 个会话都失败、且一个都没成功时立即停止，并根据错误类型给出建议（余额、key、模型名）。这次失败没有产生费用。
- **中转站上没有 Claude 模型。** 第二个 key 对应的中转站只提供 5 个 GPT 模型。先用 `profile models` 列出模型确认，再加上 OpenAI 兼容格式的支持。
- **记忆文件里的转义字符。** 头部是 YAML 格式，双引号字符串里的 `\` 和 `\"` 需要还原，否则路径会显示成 `G:\claude网站`。
- **中转站支持哪种接口格式。** 中转站通常标注为 OpenAI 格式，但在不带 key 的情况下请求 `/v1/messages` 返回的是 401（key 无效）而不是 404（地址不存在），说明它同时支持 Anthropic 格式，鱼巢可以直接接入。再用 `profile models` 列出中转站上 Claude 模型的确切名称。
- **测试预期写错。** 写测试时手算「应该剔除几个引用」算错了一次，漏掉了一条整条被丢弃的结论本身也带着一个无效引用。程序是对的，改的是测试。

### 已知的不足

- 画像的质量依赖模型，程序只能保证「每句话都有出处」，保证不了「归纳得准确」。出处可以点开核对，这是目前能做到的最好办法。
- 只用了用户写的话，没有用 agent 的回复，所以「agent 怎么评价这个用户」只能间接体现。
- 统计按本机时区计算。

## 2026-11-09 · M4 配置管家

### 结果

- 默认跟踪 4 个配置文件：Claude 的 `settings.json`、`CLAUDE.md`，Codex 的 `config.toml`、`AGENTS.md`；其他文件可以用 `config track` 加入
- 本机 Codex 的 `config.toml` 旁边有 23 个手工备份，Claude 的 `settings.json` 旁边有 8 个，命名五花八门。**导入了 27 个**，另有 2 个和已有版本内容完全相同，自动跳过；原备份文件没有改动
- Codex 配置现在有一条从 2026-07-22 到 2026-11-09 的完整时间线，Claude 配置有一条从 2026-10-02 到 2026-10-24 的时间线
- **3 个名字里带 `corrupted` 的备份，内容全部是空字节（0）**：7 月 25 日、7 月 31 日、9 月 25 日，同一种故障出现了三次
- 回滚前的预览、损坏版本的拒绝、回滚后的撤销都由测试覆盖；没有在用户真实的配置上执行回滚
- 测试从 58 个增加到 70 个

### 关键决定

**1. 先整理已有的备份，再谈以后的记录。**
用户已经用「复制一份、改个名字」的方式备份了几十次，这些就是现成的历史。按「和配置文件同名开头、后缀里带 bak / backup / corrupt / orig / save」识别出来，按文件的修改时间排进同一条时间线。修改时间代表这份内容真正写下的时间，比文件名里的日期（复制备份的时间）更准确。

**2. 每个版本都检查格式。**
JSON 用 `JSON.parse`，TOML 用 `smol-toml` 解析。解析失败的版本标为损坏并记录原因。校验规则改进后，启动时会用新规则重新检查已有版本，旧记录的结论跟着更新。

**3. 内容按哈希去重存放。**
版本表只记「哪个文件、什么时间、哪个哈希」，内容单独存一份。同一份内容出现多次只存一次。只有内容真的变了才记新版本。

**4. 自动快照搭在 `index` 上。**
不需要后台常驻程序：用户每次运行 `yuchao index` 时，顺手检查配置有没有变化，有变化就记一版。配置的历史就这样自然积累起来。

**5. 回滚是鱼巢第一个会修改文件的功能，所以做了四层保护。**
- 不加 `--yes` 只显示改动预览，不写文件
- 目标版本格式损坏时拒绝，除非明确加 `--force`
- 写入前先把当前内容存成一个版本，回滚之后也能撤销
- 先写到同目录的临时文件，再改名替换原文件；写完重新读取，核对哈希

第四点是看到那 3 个全是空字节的备份之后更确定要做的：直接覆盖写入时程序崩溃或断电，就会留下这样的文件。先写临时文件再改名，原文件要么是旧内容，要么是新内容，不会出现一半。

**6. 保存原文，显示打码。**
回滚需要原文，所以数据库里存的是原文。但命令行和网页上显示的一律打码：通用的密钥规则之外，字段名里带 key、token、secret、password 的值也遮住。纯数字的值（例如 `token_limit = 240000`）不打码。

**7. 网页只读。**
和画像一样，网页上只能看时间线和差异，回滚只能在命令行里执行，页面上给出可以复制的命令。

### 踩过的坑

- **损坏的备份把终端搞乱了。** 对比差异时打印了 5000 多个空字节。先检测内容里有没有空字节，有就不逐行对比，直接说明「已损坏」。
- **打码过度。** `model_auto_compact_token_limit = 240000` 因为字段名里有 token，数字也被遮住了。纯数字不可能是密钥，排除掉。
- **差异的顺序。** 替换一行时，最初先输出新增再输出删除，和 git 的习惯相反。最长公共子序列回溯时，平局要优先选删除。
- **测试读到了真实的用户目录。** 本地服务原来直接用默认目录，测试时会读到本机的 `~/.claude`。改成把目录作为参数传入，测试一律用临时目录。

### 已知的不足

- 只有运行 `yuchao index` 或 `config snapshot` 时才会记录，两次运行之间的多次修改只会留下最后一版。
- `~/.claude.json` 这类程序每次启动都会改写的状态文件没有默认跟踪，否则时间线会被无意义的变化淹没。
- 回滚时如果 Claude Code 或 Codex 正在运行，它们退出时可能把配置写回去，命令行会提醒先关掉。

## 2026-11-09 · 接入 WorkBuddy 和 DeepSeek Harness

### 做了什么

用户平时不只用 Claude Code 和 Codex，还用 WorkBuddy（腾讯 CodeBuddy 系的桌面 agent）和 DeepSeek Harness（dsh）。先在本机找到这两家的数据目录，摸清格式，再把解析层改成适配器注册表，最后接入。

结果：4 个 agent、251 个会话文件、2 GB，全部解析成功，0 报错。WorkBuddy 59 个会话，DeepSeek Harness 27 个（其中 9 个是子 agent）。安全扫描的发现从 24 个涨到 83 个，新增的大部分是用户在 WorkBuddy 里直接粘贴的 API key。

### 关键决定

**1. 适配器注册表。**
原来 `'claude' | 'codex'` 写死在十几个地方：索引、命令行参数、服务端、画像、配置管家、网页。现在每个 agent 是 `src/core/agents.ts` 里的一项：数据目录、怎么找会话文件、解析函数、默认跟踪哪些配置。其他模块只遍历这张表。接入新 agent 不需要改索引和界面。

**2. 数据目录按 agent 传入，没传的不读。**
`SourceDirs` 从固定的两个字段改成「agent → 目录」的映射。测试只传临时目录，就不会读到本机真实的 `~/.workbuddy`。

**3. 分清人写的话和系统塞进去的话，规则因 agent 而异。**
- WorkBuddy 的用户消息里有大段系统提示，人写的话包在 `<user_query>` 里
- DeepSeek Harness 的 `user/message` 事件有 11 种来源，只有 `source.kind = user` 是人写的，运行时上下文、时间、技能目录、队友消息等都归为上下文

**4. 不凭文档猜格式。**
OpenCode、Gemini CLI 本机没装，没有真实数据可以验证，这次不接。

### 踩过的坑

- **Node 解不开多帧 zstd。** DeepSeek Harness 每写一批事件就追加一个独立的 zstd 帧，一个会话文件有几千帧。`zstdDecompressSync` 只解第一帧（4 MB 的文件只解出 252 字节），流式解压遇到第二帧报 `Unknown frame descriptor`。
- **按魔数切帧会静默丢数据。** 第一版按帧头的魔数 `28 B5 2F FD` 切开，解压失败就和下一段合并。写测试时发现：帧被截断时 Node 不报错，而是静默返回空内容或部分内容，「失败再合并」的前提不成立。改成按 RFC 8878 读帧头和每个块头，直接算出帧的长度，不解压就能找到边界。拿真实数据对比，有一个会话文件按魔数切丢了 92 个事件（578 对 670），按格式切一个不少，13608 帧、0 字节剩余。
- **一个汉字被切在两帧之间。** 帧边界不保证落在行尾，甚至不保证落在字符边界。用 `StringDecoder` 跨帧拼接，测试里专门把「巢」的 3 个字节切到两帧。
- **压缩摘要重复计数。** WorkBuddy 压缩上下文时生成 `<cb_summary>`，把之前每一句 `<user_query>` 原样重放。不处理的话，用户的话会被重复统计。带 `<cb_summary>` 的整条算上下文后，用户消息从 491 条降到 454 条。
- **扫描报告的上下文漏了原文密码。** 一段 Python 脚本里写着 `('IP', 'root', '密码')`，没有规则认识这种写法，于是上下文打码时漏掉了；同一段里的「（base64url 字符」反倒被误判成密码。新增一条规则识别成组写出的地址、用户名、密码；含非 ASCII 字符、以 @ 开头、全大写常量名的值不算秘密。

### 已知的不足

- DeepSeek Harness 的会话文件整份读进内存再逐帧解压，目前最大的只有 4 MB，以后如果出现几百 MB 的会话需要改成流式。
- WorkBuddy 改写消息重发后，旧分支仍留在文件里，可能出现两条相似的用户消息。

## 2026-11-09 · M5 桌面应用与服务器面板

### 做了什么

- 打包成单文件程序 `yuchao.exe`（90 MB），双击即可：更新索引、启动本地网页、打开浏览器。命令行用法和源码一样
- 服务器面板：命令行 `yuchao server` 和网页「服务器」页，显示服务是否在运行、本机和公网访问、磁盘和内存、线上 release 和发布记录、最近 7 天的服务告警和 nginx 错误日志

接上用户自己的服务器当天就查出两件事：磁盘已用 86%（服务器上积累了 136 个 release 目录），以及最近 7 天服务异常退出 22 次。

### 关键决定

**1. 只读，并且在服务器那一侧保证只读。**
「鱼巢的代码不去改服务器」只是一种约定，代码有 bug 或密钥被偷时就不成立了。所以给鱼巢单独生成一把 ed25519 密钥，在服务器的 `authorized_keys` 里写成 `restrict,command="python3 status.py" ...`：这把密钥登录后只能运行状态脚本，客户端要求执行的命令会被替换，端口转发和终端也被关掉。部署后实测了三种越权方式：执行 `touch` 创建文件（文件没有出现，返回的仍然是状态 JSON）、端口转发（administratively prohibited）、申请终端（PTY allocation request failed），都被拒绝。

**2. 状态脚本用 Python 写、输出 JSON。**
服务器上本来就有 Python 3，只用标准库，不需要安装任何东西。用 bash 拼 JSON 很难处理好转义。本机用 zod 校验 JSON 的结构，脚本版本对不上时给出明确提示，而不是界面上出现一堆 undefined。

**3. 不自动信任陌生主机。**
ssh 参数里固定 `StrictHostKeyChecking=yes`、`BatchMode=yes`、`IdentitiesOnly=yes`：服务器指纹必须已知，不弹密码框，只用这一把密钥。用户名和主机名用白名单格式校验，挡住 `-oProxyCommand=...` 这种伪装成 ssh 参数的输入；参数用数组传给 `execFile`，不经过 shell。

**4. 本地记一份上线记录。**
服务器上的 release 目录可能被清理掉。每次检查时如果线上版本和上次不同，就在本地数据库里记一笔。

**5. 单文件程序用 Node 自带的 SEA，而不是 Electron。**
鱼巢本来就是「本地服务 + 浏览器界面」，不需要 Electron 再带一个浏览器内核。SEA 用的就是开发时的同一版 Node，内置的 `node:sqlite` 和 zstd 解压都能直接用。

### 踩过的坑

- **SEA 只支持 CommonJS 入口。** 命令行入口用了顶层 await，esbuild 转成 CommonJS 时会报错。把主流程包进一个 async 函数。
- **打包后找不到网页文件。** 原来按 `import.meta.dirname` 找 `web/dist`，打包后这个路径不存在。改成把网页文件作为 SEA 的内置资源，运行时用 `node:sea` 的 `getAsset` 读取。顺手把静态文件的路径检查改成逐段检查，带 `..`、反斜杠和盘符的路径一律拒绝，并补了测试。
- **端口被占用时程序卡住。** `server.listen` 出错时不会调用回调，而是触发 error 事件，原来的写法会一直等下去。现在会提示「鱼巢可能已经在运行」；双击 exe 时直接打开已经在运行的那一个。
- **服务器上的密钥登录是关着的。** `sshd_config` 里写着 `PubkeyAuthentication no`，只加 `authorized_keys` 不会生效。征得用户同意后，先备份配置，只改这一行，用 `sshd -t` 校验通过后 reload（不是 restart，已有的连接不受影响），密码登录保持不变。
- **Windows 上 npx 必须经过 shell，node.exe 的路径又有空格。** 打包脚本里只对 npx 开 shell。

### 已知的不足

- exe 没有代码签名，Windows 可能提示「未知发布者」。
- 没有做回滚和部署锁：用户选择了只读。真要做的话，需要另一把权限更大的密钥，应该单独设计。
- 状态脚本顶部的服务名、目录是按这台服务器写的，换服务器需要改几个常量。

## 2026-11-10 · 界面改版

### 做法

先写任务书（`docs/ui-brief.md`）再动手：列出现有界面的 9 个问题、要做成什么样、明确不做什么、怎样算做完。改完后逐条对照。

### 改了什么

- **框架**：顶栏换成左侧导航。原来搜索、筛选、复选框、按钮全挤在顶栏，而且只对会话页有用；现在全局操作（更新索引、显示原文、明暗切换）在导航栏底部，搜索和筛选回到会话页里。
- **概览页（新首页）**：一行总数，四张状态卡片（泄露的秘密、配置、服务器、各 agent 会话数），最近的会话。5 秒内能回答「这是什么、现在是否正常」。只用已有接口拼出来，后端没有改动。
- **会话页**：列表按日期分组；正文渲染 Markdown（代码块带复制按钮、表格、列表、行内代码）；`/` 或 `Ctrl+K` 聚焦搜索。
- **地址**：页面和打开的会话写进地址（`#/sessions/<id>?seq=<n>`），刷新、前进后退都不丢位置。
- **其他**：明暗模式可手动切换并记住；加载时显示骨架占位；命令提示统一成 `yuchao ...` 并带复制按钮；窄窗口下导航收成图标条，会话页一次只显示列表或正文。
- **设计规范**：颜色、间距、圆角、字号全部是 CSS 变量，只在一处定义。

### 关键决定

**1. Markdown 渲染器自己写，不引入库。**
会话内容来自 agent 和工具输出，是不可信的。自己写的解析器只产出数据结构，里面根本没有「原始 HTML」这种节点，渲染时只生成 React 节点，不使用 `dangerouslySetInnerHTML`；链接也不生成可点击的 `<a>`。测试里放了 `<script>`、`onerror` 和 `javascript:` 链接，确认它们只会被当成文字。解析和渲染分成两个文件，解析部分是纯函数，可以直接用 `node --test` 测。

**2. 不引入组件库、图标库、CSS 框架。**
图标是 19 个内联的 SVG 路径。改版后 JS 压缩后 84 KB（改版前 79 KB）。

**3. 状态不只靠颜色。**
正常、警告、错误都是「图标 + 文字」，颜色只是辅助。agent 的标签从四种颜色的实心色块改成「小圆点 + 名字」，不再比标题抢眼。「显示原文」打开时顶部有一条醒目的提示，避免截图时忘记关。

### 踩过的坑

- 会话页头吸顶时，子 agent 多的会话页头占了半屏。只让标题和一行信息吸顶，其余跟着正文滚动。
- 明暗模式如果等 React 启动后再设置，深色用户会先看到一下白屏。改成在 `index.html` 里用一小段内联脚本提前设置。
